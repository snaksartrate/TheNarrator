# TheNarrator
### A Comparative Study on Story Generation Using Small Language Models

## 1. Project Overview

TheNarrator is a Machine Learning project focused on building a basic **Small Language Model (SLM)** capable of generating short stories.

The primary objective is to study how different training strategies and tokenization methods influence the quality of stories generated by a language model.

Instead of building just one model, we will train multiple model variants using different combinations of training strategies and tokenization patterns, then compare their outputs.

This is primarily an experimental and comparative study.

## 2. Research Objective

Our central research question is:

**How do different training strategies and tokenization patterns influence the quality, diversity, coherence and efficiency of stories generated by a small language model?**

We have two experimental dimensions.

### A. Training Strategies

We will compare two training strategies:

1. AdamW optimizer with a fixed learning rate.
2. SGD optimizer with momentum.

### B. Tokenization Methods

We will compare three tokenization approaches:

1. **Character-level:** Text is divided into individual characters.
2. **Word-level:** Text is divided into individual words.
3. **Subword-level (BPE):** Text is divided into frequently occurring subword units using Byte Pair Encoding.

### C. Experimental Matrix

| | Character | Word | BPE |
|---|---|---|---|
| AdamW | Model 1 | Model 2 | Model 3 |
| SGD + Momentum | Model 4 | Model 5 | Model 6 |

**Total models = 2 training strategies × 3 tokenization methods = 6 models.**

All six models will use the same underlying Transformer architecture.

The dataset splits and experimental conditions will be kept consistent wherever possible so that the comparison remains meaningful.

## 3. Proposed Model Architecture

We intend to implement a basic autoregressive Transformer language model using PyTorch.

The model will include:

- Token embeddings.
- Positional embeddings.
- Masked self-attention.
- Feed-forward layers.
- Transformer blocks.
- Language modelling output layer.
- Next-token prediction.

The model will learn to predict the next token based on the preceding context and generate stories autoregressively.

We are intentionally keeping the architecture relatively simple because the primary focus is comparing training strategies and tokenization methods.

## 4. Dataset

We will use a common collection of short stories for all six experiments.

The dataset preparation process will include:

1. Selecting a suitable public-domain story dataset.
2. Collecting and organizing the raw data.
3. Cleaning malformed and empty samples.
4. Removing duplicate stories.
5. Normalizing text.
6. Splitting the dataset into training, validation and test sets.
7. Generating dataset statistics.

The exact dataset source and size will be documented once finalized.

All experiments must use consistent dataset splits to prevent data leakage and maintain experimental fairness.

## 5. Evaluation Metrics

Generated stories and trained models will be evaluated using quantitative and qualitative metrics.

| Metric | Purpose |
|---|---|
| Perplexity | Measures next-token prediction performance on held-out data |
| Distinct-1 | Measures unigram diversity |
| Distinct-2 | Measures bigram diversity |
| Repetition | Measures repeated words and phrases |
| Lexical Diversity | Measures vocabulary variety |
| Coherence | Evaluates consistency and flow of stories |
| Grammar and Readability | Evaluates linguistic quality |
| Generation Time | Measures story generation efficiency |

We will also manually inspect generated stories to evaluate qualities that automated metrics cannot fully capture.

**Note:** Perplexity values across different tokenization methods must be interpreted carefully because token units and vocabulary distributions differ.

## 12b. Prompt-Based Story Continuation (inference only)

Type your own story opening and compare how the six trained Transformers continue it. This
adds no training, no new model, optimizer, tokenizer or experiment. Each model uses its own
checkpoint (`best.pt`) and the tokenizer saved with it.

```bash
python main.py "A little girl discovered a mysterious key beneath her bed."
python main.py --generate "The old clock stopped at exactly midnight."
```

Optional: `--exp ID` (one model only), `--max-new-tokens N`, `--temperature F`, `--top-k N`,
`--seed N`, `--device DEVICE`, `--no-report`. Defaults match the research settings (300 new
tokens, temperature 0.8, top-k 40, sampling, seed 42), applied identically to all six models.
Equal seeds do not give equivalent samples across different tokenizers.

Output is a 3-column (character, word, BPE) by 2-row (AdamW, SGD + momentum) layout; narrow
terminals fall back to stacked panels. The prompt is context, not part of the new-token
budget; prompts longer than the 256-token window keep BOS and the newest tokens. A missing or
corrupt checkpoint marks only that model as unavailable/failed; the others still run.

Every invocation is saved in `experiments/prompt_comparisons/run_00001/` (then `run_00002`, ...
up to `run_99999`; IDs are never reused, never wrap, never overwrite). Each run holds the exact
prompt, one text file per model, JSON, CSV, a Markdown report and metadata. These runs are
illustrative demonstrations, kept separate from `experiments/outputs/` and the official
`experiments/analysis/` evaluation. They are not statistical evidence and are not mixed into the
official generated stories or human ratings.
